# Live news endpoint

`GET /.netlify/functions/news` aggregates the configured catalog of original publisher, research, clinical and policy RSS/Atom feeds. Publisher titles, dates and excerpts are retained; classification and tags use local rules, without an AI API or API key. Mixed-topic feeds must contain an AI term or recognized AI product name. Journals require explicit AI/ML terminology even if their feed is marked AI-only, so ambiguous electrical-transformer or physical-diffusion articles do not qualify. An AI topic tag or a general journal description alone is insufficient. The strict publication window is `[request time − 24 hours, request time]`, including exact boundaries and excluding every future timestamp. Atom `updated` alone cannot substitute for an original publication date. The window is enforced when parsing, deduplicating, reading stale source data and serving every cached response. Empty categories are valid when nothing qualifies.

The JSON response includes `articles`, `updatedAt` (last feed check), `servedAt`, `windowHours: 24`, `windowStart`, `newestPublishedAt`, `refreshInterval` (3600000 milliseconds / one hour), `sources` (status objects), `partial`, `stale`, and category `counts`. Articles contain `id`, `title`, `summary`, `url`, `image`, `source`, `sourceId`, `publishedAt`, `category`, `tags`, and `spotlight`. Categories are `news`, `technical`, `clinical`, `tools`, and `geopolitical`; all-news filtering shows every category. Meaningful AI regulation, international competition, chip export controls, sovereignty, defense and diplomacy take precedence, followed by clinical coverage, explicit technical research subjects and then tool launches. Generic regulatory boilerplate does not by itself turn a clinical/technical story into geopolitics. These categories are heuristics and can occasionally be imperfect.

`spotlight` contains an integer `score`, transparent `reasons`, and `corroboration` metadata. Production scores use publication recency (0–40), concrete editorial impact (0–26) and related-topic coverage across distinct publishers (up to 30), capped at 100. Generic vendor/AI words cannot create matches. A headline index narrows coverage evidence to at most 160 matching candidates per displayed story so a large feed catalog cannot cause an unbounded all-pairs comparison. Evidence comes from qualifying items before duplicate removal; feeds sharing a registry `publisher` count as one publisher. `corroboration.sourceCount` includes the article's own publisher, while `otherSourceCount` excludes it. This bounded related-topic sample is **not fact verification or measured popularity**. The endpoint keeps chronological order; clients may sort by spotlight score.

Production uses original publisher sourcing. `createNewsService` defaults both `creatorSource` and `curatorUrl` to `null`, so creator/newsletter requests and their ranking signals are disabled. Compatibility fields remain `creatorSignals: []`, `creatorStatus: null` and `curatorDispatch: null`.

Source status passes through `publisher`, `kind` and `trustReason` from the catalog. `sourceCoverage` distinguishes `configured`, `checked`, `available` (valid feed fetch, even with zero recent AI posts), `current` (at least one qualified recent item), `unavailable`, and `deferred` (time-budget limit, not evidence that a publisher is down). It also counts configured and included publishers. `sourceGroups` summarizes these feed groups by `kind`. Per-source and group item counts are before cross-feed deduplication and article capping.

The engine runs at most 16 feed requests at once and at most two per hostname. It interleaves hosts rather than issuing hundreds of sockets together, rotates the catalog starting point hourly, and stops source checks at 38 seconds. Active requests are aborted at that boundary; unstarted/incomplete checks are reported as deferred and may use still-fresh warm-cache data. Feed requests have six-second timeouts and two-megabyte limits. At most 160 entries are scanned and the newest 50 qualifying items retained per feed. Deduplication selects up to 400 stories through publisher round-robin balancing before final chronological sorting, preventing a high-volume feed from crowding every small publisher out. Thumbnail work uses the remaining 42-second API refresh budget and falls back to static artwork.

Publisher thumbnails are used when present. The twelve most recent items without RSS images also receive optional Open Graph thumbnail lookups from approved publisher hosts, with four concurrent requests, 2.5-second timeouts, a 350 KB HTML-head limit, and no redirects. Image results are cached for six hours in a warm instance. Otherwise `image` refers to `/images/{category}.svg`; these five static images must be supplied by the frontend. Remote images may be removed or blocked by their publishers, so the frontend should also handle `img` errors with this fallback. Excerpts are plain text, never trusted HTML.

The handler caches upstream fetches and coalesces concurrent requests for one hour, including failed attempts; it re-filters publication timestamps and recomputes spotlight metadata every time it serves data. Netlify CDN TTL is the lesser of remaining fetch-cache lifetime and earliest qualifying content's 24-hour expiry, rounded down. CDN stale-on-error is disabled. DTD and custom entity declarations are rejected, XML entity expansion is disabled, and public HTTP(S) links are validated. If every source fails with no qualifying cached stories the endpoint returns an honest empty 503; frontend caches must also enforce the strict publication window.

`lib/news-cache.mjs` persists one versioned raw hourly snapshot in a strong-consistency Netlify Blobs store, including coverage, per-source success timestamps and health metadata. Cold instances prefer an unexpired shared snapshot and restore per-source fallback state before any needed refresh. Every snapshot serve still runs `projectNewsResponse`: neither the Blob's existence nor its hourly TTL can extend a story past 24 hours. Original publication dates are preserved. Version, complete source-catalog fingerprint (including URLs and trust/filter metadata), timestamp/schema/URL checks and bounded 24 MB stream reads reject corrupt, future, excessively old or mismatched data. The app supports up to 350 source statuses and 17,500 coverage items per snapshot; it returns at most 400 stories. The SDK uses Netlify's automatically injected runtime context, with no new account, manual token or paid-plan configuration. Missing local/runtime Blob access logs a bounded warning and falls back to local warm fetching.

Production uses `dhivi-news-hourly-production-v1`; previews, branches, historical production deploys and local contexts use isolated store names. Warm-instance response, source and image caches and in-flight refreshes follow the same scope, so an earlier historical or prepublication request cannot make a production request reuse the isolated feed. At most four scoped workers are retained, with least-recently-used eviction. Two fixed Blob keys are reused instead of accumulating hourly files. A 55-second atomic conditional lease permits one shared refresher at a time and expires naturally if a process stops. Other instances can serve still-fresh articles from the prior snapshot while it refreshes. With no qualifying previous data, the endpoint returns `503`, `cacheStatus: "refreshing"` and `Retry-After: 5`; this short API retry does not refetch publishers under an active lease. All Blob operations have two-second overall limits, including SDK retries. Each normal shared refresh uses at most two SDK read operations and two SDK write operations; warm in-memory and CDN hits need no Blob read.

`warm-news.mjs` runs at minute zero each hour on published Netlify deployments and updates the same shared snapshot. It uses an 18-second source budget, 20-second refresh budget and existing publisher thumbnails to leave room for Blob I/O under Scheduled Functions' 30-second limit. API cold misses retain a 38-second source budget and 42-second refresh budget. Existing cached publisher images survive warming. The current `esbuild` function bundler already supports the added `@netlify/blobs` dependency; no new environment secrets are required. Production verification should confirm a cold request reports `cacheStatus: "shared"`, schedule registration, and Blob warnings in function logs.

Actual durations, memory allocation and the account's plan determine usage; no plan or billing settings are changed here. The Blob SDK permits much larger objects, but this app deliberately caps snapshots and operations. [Blobs documentation](https://docs.netlify.com/build/data-and-storage/netlify-blobs/) describes its injected authentication, consistency and storage limits.

For catalog validation, import `runSourceChecks` from `news.mjs` and `fetchFeed` from `lib/feeds.mjs`. Pass each scheduler task's AbortSignal through `fetchFeed(source, { signal, now, timeout })`, and use the same `concurrency`, `perHost` and `deadlineMs` options. Valid feeds with zero 24-hour stories remain available; deferred checks should be retried in another bounded batch rather than classified as dead feeds. Source trust reasons belong to catalog review, not an HTTP-success heuristic.

Required runtime: Node 22 or newer. Required dependencies: `fast-xml-parser` version 5 and `@netlify/blobs` version 11. Configure Netlify's functions directory as `netlify/functions` with the `esbuild` bundler. No secrets are required. The functions use Netlify's modern default-handler API.

Run meaningful parsing, security, classification and cache tests with:

```sh
node --test tests/news.test.mjs tests/news-cache.test.mjs
```

Publication cadence belongs to each source. Polling once per hour checks for new posts; it cannot guarantee a newly published story each hour.
